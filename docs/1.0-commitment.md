# What 1.0 Means

Version 1.0 is a release commitment, not a date or an adoption milestone. We will call the
dashboard 1.0 only when the product's smallest useful public surface is supported, documented,
tested, and operationally demonstrated.

The 1.0 surface is intentionally small:

- the board schema;
- the normalized panel protocol;
- supported deployment entrypoints; and
- extension contracts.

Undocumented implementation details are not compatibility commitments. Before 1.0, we may remove
or reduce anything that does not earn its place in that surface. After 1.0, documented behavior is
protected by semantic versioning.

## The 1.0 gate

### Product and integrations

- `pipeline-status` works through GitHub Actions and at least two additional CI or build
  integrations.
- Every supported integration has real contract coverage for success, failure, running, unknown,
  unauthorized, upstream failure, timestamps, and source links.
- Built-in panels remain source-agnostic; provider-specific behavior stays in server-side
  adapters.

### Deployment

- AWS has documented and verified ECS/container and Lambda deployment paths.
- Google Cloud has documented and verified Cloud Run and Cloud Functions deployment paths.
- Each of those four cloud/deployment combinations has a live reference deployment.
- The evidence covers upgrades, rollback, health checks, logs, secret configuration, and promotion
  of an immutable client version.

### Authentication and security

- BYOOAUTH is supported: operators can provide their own OAuth/OIDC identity provider or a
  compatible authenticated gateway.
- Deployed configurations are secure by default, including authentication, authorization, token
  verification, and secret isolation.
- Local unauthenticated experimentation is explicit and clearly separated from deployed defaults.
- The upstream allowlist and SSRF boundary remain intact and have security regression tests.
- Remote widgets and future data-source extensions have a documented trust, isolation, origin, and
  versioning model before they are accepted as 1.0 capabilities.

### Extensibility

- Independently hosted or CDN-hosted panel/widget additions can be used without forking or
  rebuilding the dashboard.
- At least two independently hosted widget examples exist.
- At least one independently hosted/custom data-source example exists once its hosting model is
  selected and documented.
- The extension contract documents lifecycle, data envelope, failure behavior, version pinning,
  and security limitations.
- Custom extensions preserve honest loading, stale, error, and status semantics.

### Radiator usability and resilience

- The layout works at wall scale and on narrow screens, supports reduced motion, and is usable
  with keyboard and screen readers.
- Every panel visibly distinguishes loading, healthy, stale, unknown, and source-error states.
- Status is always communicated with glyphs and labels as well as color.
- Browser tests cover representative boards and all supported panel states.

### Contribution and release discipline

- Contributor documentation states the minimum supported API, simplicity and dependency rules,
  testing expectations, and compatibility policy.
- `npm run check` remains the normal, fast feedback loop and passes before release.
- Releases include a version, changelog notes, dependency and image review, reproducible artifacts
  or checksums, and rollback guidance.
- No adoption-count requirement applies. Technical, operational, and security evidence is enough.

## Mandatory evidence

No 1.0 release is made on documentation or intent alone. The release must be demonstrated by real
contract tests, published documentation, and live reference deployments covering every required
cloud and deployment form above.

The architecture for externally hosted source adapters may remain open while the product evolves,
but it must be resolved and documented before the related extension criterion can be accepted. If a
criterion is not met, the release remains pre-1.0 and the missing evidence is stated plainly.
